# 每日训练计划与提醒

计划由 SQLite 按当前档案保存，包含每日有效完成会话目标（1–20 次）、模式（全部/轨迹/反应/协调）、本地提醒时间和提醒开关。关闭提醒仍保留目标。删除计划需二次确认，不删除档案或训练记录。缺少档案时编辑页提示先建立档案，调度器安全取消任务。

## 调度与真实通知

`ReminderScheduler.sync(Context)` 读取当前档案、计划和已安排任务的指纹；同一计划已有 PendingIntent 时保留该任务，避免用户在闹钟到点而系统尚未投递时打开应用，导致当天提醒被跳过。修改、关闭、删除或切换档案时先使旧任务失效并取消，再按新状态安排唯一任务。实际调度使用 `AlarmManager.RTC_WAKEUP` 的一次性 `setAndAllowWhileIdle` 非精确闹钟。它不使用循环定时器、后台常驻服务或精确闹钟权限，因此不承诺精确到分钟；系统省电、强行停止应用及厂商后台限制可能延后或阻止投递。普通应用启动调用 sync 恢复状态。

触发时，`ReminderReceiver` 检查代际编号、档案和完整计划指纹；旧任务即使已进入广播队列也无法恢复已取消的提醒。有效触发会先安排下一次，再通过渠道 `daily_training` 发布真实系统通知。点击通知使用 `destination=plan` 打开 MainActivity 计划页。通知内容说明每日目标与训练模式。

每日时间按 `ZoneId.systemDefault()` 和本地日历日期计算，而非简单增加 24 小时，因此适应夏令时的 23/25 小时日。夏令时跳过的时间顺延到合法本地时间，重叠时间采用较早偏移。SharedPreferences 持久保存“档案 ID + ISO 本地日期”的已投递集合，保证同一档案同一本地日期最多一次，重启、重复广播或切换时区不会清空去重信息。无权限而未发布的通知不记为已投递；恢复权限后从下一个计划提醒时间生效。

`BootReceiver` 接收 `BOOT_COMPLETED`、`TIME_SET`、`TIMEZONE_CHANGED`、`MY_PACKAGE_REPLACED` 后调用 restore 强制取消并按当前本地时间重排。设备关机期间不补发历史提醒，下一次为未来最近的计划时间。普通恢复和系统时间重排会保留通知栏中用户尚未处理的提醒；修改、关闭或删除计划才撤销相关旧通知。应用被用户强行停止后，Android 在用户重新打开应用前可能不再向其发广播，这是系统行为。

## 权限与用户反馈

Android 13+ 在用户保存已开启提醒的计划时请求 `POST_NOTIFICATIONS`。拒绝或关闭通知不影响计划保存及正常训练，编辑页明确提示无法显示通知，并提供再次授权和系统通知设置入口。设置页同时考虑应用通知总开关和本渠道开关。Receiver 再次检查权限，并处理检查与发布间权限被撤销的竞态。

SQLite 写入失败时，保存页会说明修改尚未保存并保留输入，删除失败会保留原计划并说明可重试；数据库已保存但系统调度失败时另行说明“计划已保存，但无法安排提醒”，避免将两种状态混为一谈。

Manifest 应包含 `POST_NOTIFICATIONS`、`RECEIVE_BOOT_COMPLETED`，注册非导出的 `PlanActivity`、`ReminderReceiver` 和接收上述系统事件的 `BootReceiver`；不声明 `SCHEDULE_EXACT_ALARM` 或 `USE_EXACT_ALARM`。

## 验证

`ReminderSchedulerTest` 使用 Robolectric 验证缺档案、修改/关闭/删除取消旧任务、单次通知后的重排、过期广播失效、按本地日期持久去重、通知关闭时不误记已投递、重启及时间变化恢复、真正按新时区计算触发时刻、夏令时跨日的 23/25 小时计算，以及前台恢复保留延迟闹钟和已显示通知。`PlanActivityTest` 验证缺档案保护、输入范围、删除二次确认，并用 SQLite 拒绝写入触发器验证保存和删除失败可恢复。`NotificationPermissionTest` 在 SDK 33 验证真实运行时权限拒绝与授予、应用通知总开关、渠道禁用及通知点击目标。

真实设备验收：保存当前时间后一两分钟的开启计划，允许通知并观察系统通知；点击进入计划页；再分别拒绝权限、关闭/删除计划和重启设备验证对应行为。系统可能延迟非精确闹钟，验收不应以秒级准时作为通过条件。
